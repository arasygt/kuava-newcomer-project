# LEARNING

Open Questions from the pipeline that I could not answer at first, what they mean in my own words, and the answer I finally gave.

| Open Question | What it means, in my own words | My final answer |
|---|---|---|
| **OQ-1** — What happens with an MP4 whose codec is not H.264? | ".mp4" is only the *box* (container) the video is packed in. Inside it the pictures can be compressed with different codecs (H.264, MPEG-4 Part 2, H.265…). A file can be a real MP4 and still not be H.264. | Accept only `.mp4` files whose video stream is H.264; reject everything else with a clear message and delete the upload. |
| **AQ-4** — How do we detect H.264 without FFmpeg? | Every MP4 starts with an `ftyp` box (bytes 4–8). The codec is identified by a 4-letter **FourCC** code such as `avc1` or `h264`, which OpenCV can read. | Check `ftyp`, then the FourCC (`avc1/avc3/h264/x264`), then decode the first frame to be sure the file is not corrupt. |
| **AQ-3** — How do we make sure the frame shown for selection is exactly the frame the tracker starts on? | H.264 stores full pictures only every so often (**key frames**); the frames in between only store differences. Jumping to a frame number can land on the nearest key frame instead, so you get a slightly different frame. | Don't seek. Decode frame by frame (`grab()`) up to the wanted frame, for both the selection image and the tracker. |
| **OQ-6 / AQ-6** — Which OpenCV tracker should be the default? | CSRT, KCF and MIL are different tracking algorithms. CSRT is the most accurate and can follow size changes but is slow; KCF is very fast but keeps a fixed box size; MIL handles partial occlusion but is the slowest. | KCF by default, because on my 2-core laptop CSRT took ≈ 40–50 ms per frame (≈ 45 s for 900 frames, too close to the 60 s limit) while KCF does a 30 s 720p video in ≈ 10 s. CSRT and MIL can still be chosen. |
| **OQ-9** — What does "the box is inside the zone" mean? | There are several possible rules: the whole box inside, only the centre inside, or a minimum overlap (e.g. IoU). The choice changes the lock times a lot. | The whole box must be inside; touching the border still counts as inside. |
| **OQ-11** — Is there a minimum duration for a lock to count? | In TEKNOFEST a lock only counts after it is held for 4 seconds. The task asks to report *every* continuous period, so we had to decide whether to filter short ones. | No minimum. Every period of at least one frame is listed and the longest one is highlighted. |
| **OQ-17** — Is an area change of exactly 50% a loss? Compared to which frame? | A boundary question: "more than 50%" must be turned into an exact formula, otherwise the tests cannot know what to expect at exactly 50%. | Lost when `abs(A_now − A_previous) / A_previous > 0.5` (strictly greater), compared with the previous frame's box. Exactly 1.5× or 0.5× the area is still tracked; tests check 150 / 150.01 and 50 / 49.99. |
| **AQ-11** — Does tracking on a smaller (downscaled) frame change the 50% rule? | We track on frames resized to 640 px wide to save time. If both boxes are scaled by the same factor, their area ratio stays the same. | No effect: the ratio is scale-invariant. Boxes are converted back to original pixels before the check anyway. |
| **IQ-4** — How do I turn the browser's video time into a frame number? | The `<video>` element gives a time in seconds, not a frame index. Rounding the wrong way puts the box of the previous frame on screen. | `frame = floor(time × fps + 0.0001)`, and when jumping to a frame I seek to the *middle* of that frame (`(f + 0.5) / fps`). |
| **Testing term** — What are "red phase" and "boundary triples"? | Red phase: write the tests before the code and watch them fail, which proves they can catch a missing feature. Boundary triple: for every limit L, test exactly L, just below L and just above L. | Every story was committed with its failing tests first (results in the implementation log). Limits such as the 4×4 px minimum box, the zone edges and the 50% rule each have L / L−ε / L+ε tests. |
