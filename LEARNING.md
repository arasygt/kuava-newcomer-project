# LEARNING

Open Questions from the pipeline that I could not answer at first (or answered wrong at first), what they mean in my own words, and my final answer.

| Open Question | What it means, in my own words | My final answer |
|---|---|---|
| **OQ-9**: What does "the box is inside the zone" mean? | I did not know there were different ways to say "inside". It could mean the whole box is inside, only the centre of the box is inside, or the box overlaps the zone by some amount. Each rule gives different lock times. | The box must be inside the zone as a whole. Touching the border still counts as inside. |
| **OQ-11**: Is there a minimum duration for a lock to count? | In TEKNOFEST a lock only counts after 4 seconds. At first I thought we should only show locks longer than 4 s to be realistic, but the task says to report *every* continuous lock period. | No minimum. Every lock period is listed, even one frame long. The longest one is highlighted, so you can still see if it is over 4 s. |
| **OQ-16**: After tracking is lost, should the tracker continue or stop? | I was not sure at first. After a loss the tracker may be following a cloud or nothing, so the boxes after that are wrong and could count as fake lock time. | Stop at the loss frame. The user must select the target again (on any frame where it is visible, OQ-18). Results before that frame are kept. |
| **AQ-1**: Which language/framework should the app use? | I first only thought "Python is simple and has many libraries". The real reason is that the task needs OpenCV trackers, and they work best in Python. The app also has to start with one command. | Python + FastAPI for the server, plain HTML/JS in the browser (no build step). OpenCV trackers and pytest are easy in Python, and the app runs with `python run.py`. |
| **AQ-3**: How do we make sure the frame shown for selection is exactly the frame the tracker starts on? | H.264 only stores a full picture now and then (key frames). The other frames only store what changed, so they need the frames before them. If you jump straight to a frame you can land on a slightly wrong one, and the box would be misaligned from the start. | Never jump. Decode the video frame by frame (`grab()`) until the wanted frame, so it is exact. |
| **AQ-8**: Should the lock logic run in the browser or on the server? | I did not know. The task wants the lock logic tested with generated box sequences that have known answers. If the logic is plain Python, pytest can test it directly without a browser. | On the server, as a pure Python module (`app/lock.py`). The browser only draws the results. |
| **IQ-1**: How do we get H.264 test videos without committing video files? | Tests need real videos, but large videos must never be committed. I guessed we generate them. | The tests generate small H.264 videos while they run (imageio-ffmpeg) in a temporary folder. Nothing is committed, and because we drew the moving target ourselves we know its true position on every frame. |
| **IQ-5**: How can tests check exact lock periods when a real tracker's boxes wobble a pixel or two? | I did not know. The trick is to skip the tracker in the test: we write the boxes ourselves, so we know the exact answer. | Most tests feed the server a list of boxes we wrote (`set_states`) and check the exact periods. One end-to-end test uses a real tracker and allows ±2 frames. |
| **IQ-7**: Real trackers do not fail on a predictable frame. How do we test the exact loss frame? | I did not know. Same idea as IQ-5: replace the part we cannot control (the OpenCV tracker) with a fake one that follows a script. | A fake tracker fails on a chosen frame and we check the run stops exactly there. A second test runs real KCF on a video where the target disappears on frames 30–39 and checks the loss is in that range. |
